# Day 52 – Kubernetes Namespaces and Deployments

## Task 1: Explore Default Namespaces

Kubernetes comes with built-in namespaces. List them:

kubectl get namespaces

You should see at least:
```
default — where your resources go if you do not specify a namespace
kube-system — Kubernetes internal components (API server, scheduler, etc.)
kube-public — publicly readable resources
kube-node-lease — node heartbeat tracking

kubectl get pods -n kube-system
These are the control plane components keeping your cluster alive. Do not touch them.
```

## Task 3: Create Your First Deployment

A Deployment tells Kubernetes: "I want X replicas of this Pod running at all times." 
If a Pod crashes, the Deployment controller recreates it automatically.

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
  labels:
    apps: frontend-dev
  namespace: dev
spec:
  replicas: 3
  selector:
    matchLabels:
      apps: frontend-dev
  template:
    metadata:
      labels:
        apps: frontend-dev
    spec:
      containers:
        - name: frontend
          image: rohit5126/devboard-frontend:latest
          ports:
            - containerPort: 4173
```
```

kubectl get deployments -n dev

kubectl get pods -n dev (3 pods running)

```
READY: Displays the number of running Pods that are ready to accept traffic against the total number of desired Pods.

UP-TO-DATE: Shows how many Pods are running the latest, updated configuration (matching the current Deployment template).

AVAILABLE: Indicates how many of those updated Pods are currently available to take work or serve traffic. 
It accounts for the time a new Pod has been up without crashing

## Task 4: Self-Healing — Delete a Pod and Watch It Come Back

```
# List pods
kubectl get pods -n dev

# Delete one of the deployment's pods (use an actual pod name from your output)
kubectl delete pod <pod-name> -n dev

# Immediately check again
kubectl get pods -n dev
```

Is the replacement pod's name the same as the one you deleted, or different?

## Task 5: Scale the Deployment

```
  201  kubectl get pods -n dev

  203  kubectl scale deployment -n dev frontend --replicas=2
  204  kubectl get pods -n dev

```
You can also scale by editing the manifest — change replicas: 4 in your YAML file and run kubectl apply -f nginx-deployment.yaml again.

`When you scale down your application, Kubernetes gracefully terminates the 3 extra pods to match your new desired state. It stops sending them new traffic, 
allows them to finish their active tasks, and then deletes them to free up compute resources`

## Task 6: Rolling Update

```
kubectl set image deployments/frontend -n dev frontend=nginx:latest
                  {deployment with name}      {conatiner_name = new image }
    
  215  kubectl rollout status deployment/frontend -n dev   (live status)

  217  kubectl get pods -n dev
  218  kubectl set image deployments/frontend -n dev frontend=nginx:1.25

  219  kubectl rollout status deployment/frontend -n dev

  220  kubectl get pods -n dev

  222  kubectl rollout history deployment/frontend -n dev  ( this shows all the rollout version with number)

  223  kubectl rollout undo deployment/frontend -n dev  ( go back to previous rollout version)

  224  kubectl rollout history deployment/frontend -n dev

  225  kubectl describe deployment frontend -n dev | grep Image (to see the current imaeg of the deployment)
  226  kubectl rollout undo deployment/frontend -n dev 
  227  kubectl describe deployment frontend -n dev | grep Image

```
