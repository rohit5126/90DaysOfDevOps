# Resource Requests, Limits, and Probes

In Kubernetes, a **Resource Request** specifies the minimum amount of **CPU and memory (RAM)** that a container needs to run reliably. 
It serves as a guaranteed baseline reserved for your workload. The kube-scheduler uses these requests to decide which worker node can accommodate your Pod. 
If a node lacks enough unreserved capacity to satisfy the request, the Pod will not be placed there, protecting against resource starvation.

**Resource Limits** specify the maximum amount of **CPU and memory (RAM)** that a container is allowed to consume. While requests guarantee a minimum baseline, 
limits act as a strict hard ceiling to prevent a single misbehaving or traffic-heavy container from hogging a worker node's entire resource pool and crashing neighboring applications.

## Task 1: Resource Requests and Limits

```
apiVersion: v1
kind: Pod
metadata:
  name: firstpod 
  labels:
    app: myapp
spec:
  containers: 
    - name: nginx
      image: nginx:latest
      ports:
        - containerPort: 80
      resources:
        requests:
          cpu: "200m"
          memory: "128Mi"
        limits:
          cpu: "200m"
          memory: "128Mi"
```

Since requests and limits differ, the QoS class is Burstable. If equal, it would be Guaranteed. If missing, BestEffort.

metadata:
  name: stresspod 
  labels:
    app: stress

## Task 5: Readiness Probe

Kubernetes provides readiness probes to detect taht pod is not ready for the requests. it usually used in Db as it takes time get setup.
until its ready it will not reciev request from kubernetes service.
A pod with containers reporting that they are not ready does not receive traffic through Kubernetes Services.

```
readinessProbe:
            exec:
              command: ["sh","-c", "pg_isready -U $(POSTGRES_USER) -d $(POSTGRES_DB)"]
            initialDelaySeconds: 60
            periodSeconds: 10
```

## Task 6: Startup Probe


A startup probe is a Kubernetes diagnostic used to determine if an application within a container has successfully initialized. It is specifically designed for slow-starting 
containers, as it disables liveness and readiness checks until it succeeds, preventing Kubernetes from prematurely killing the container

```
startupProbe:
  httpGet:
    path: /health
    port: 8080
  failureThreshold: 30
  periodSeconds: 10
```
